# 性能基准

## 2026-11-25 · M1 本地引擎

- 机器：Windows 11，24 线程 CPU，RTX 5060 8GB（通过 DirectML 调用）
- 样本：《常微分方程（第四版）》王高雄，第 11–30 页（纯扫描件，516×728 pt）
- 渲染：PDFium chromium/8179，200 DPI（约 1433×2022 px）
- 排版解析：multi_para
- 命令：`anyocr bench <pdf> --pages 11-30 --model <m> --device <d> --workers <n>`

| --------------- | -------------------- | ------ | ---------- | -------- | -------- | ---------- |
| PP-OCRv6 small  | CPU                  | 1      | 38.7 s     | 1.94     | 14382    | 0.956      |
| PP-OCRv6 small  | CPU                  | 2      | 19.3 s     | 0.96     | 14382    | 0.956      |
| PP-OCRv6 small  | CPU                  | 3      | 39.5 s     | 1.98     | 14382    | 0.956      |

| PP-OCRv6 medium | DirectML             | 1      | 26.0 s     | 1.30     | 14028    | 0.957      |

冒烟测试：《杨氏模量》课本扫描件 4 页，CPU 单实例，5.1 s，平均置信度 0.954，正文中文基本无误。

结论与默认值：

- 默认 **PP-OCRv6 small + 自动设备（有 GPU 时用 DirectML）+ 单实例**。按这个速度，264 页的整本书约 3 分钟。
- 纯 CPU 时默认 2 个实例。实例数不能多开：3 个实例时线程互相抢占，反而和单实例一样慢。
- DirectML 多实例会严重变慢，GPU 模式固定为单实例。
- 追求速度时选 tiny：识别字符数几乎不变，但 DirectML 下置信度明显偏低（0.908），这类场景适合配合 VLM 复核。
- 渲染只占总耗时约 5%，瓶颈在 OCR 推理。
- 后续优化方向：GPU 检测与 CPU 识别混合流水线，以及让识别阶段批量处理文本行（region batch）。

- 整本平均 1.07 秒/页，比第 11–30 页基准（0.73）慢：全书含大量公式、目录等文本块密集的页面。
- 抽样搜索使用 PDFium 的搜索接口（即 Chrome / Edge 的 Ctrl+F 实现），每页在首、中、末三行内各取 4 个字。少量未命中来自 PDFium 在行内自动插入空格。
